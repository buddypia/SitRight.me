# Feature Spec Generator

> **Core Concept**: Converter from intent to contract ("Intent to Contract")

This skill takes **User Stories, Why (Purpose), and Requirements** entered by developers and transforms them into concrete contract documents (SPEC/Screen) that AI can implement.

## Input Format

> **Mandatory Prerequisite**: `CONTEXT.json` must already exist.
> CONTEXT.json is created by **feature-architect**. This skill uses CONTEXT.json in **read-only** mode.

### Required Inputs

| Input | Description | Example |
| --- | --- | --- |
| **Feature ID** | ID assigned by feature-architect | `001-user-dashboard` |
| **CONTEXT.json** | Present in feature directory | `docs/features/001-user-dashboard/CONTEXT.json` |

### Optional Additional Inputs

Used to supplement or clarify information in CONTEXT.json:

| Input Type | Description | Example |
| --- | --- | --- |
| **Additional Requirements** | Detailed requirements not present in CONTEXT | "Support offline sync" |
| **Constraints** | Additional technical/business constraints | "Reuse existing data structures" |

## Protocol

### PATH CONTRACT (MANDATORY)

> **BINDING**: This skill uses dynamic path placeholders.
> The AI must resolve paths from `project-config.json` before performing file operations.
> Using literal paths is a **protocol violation**.

| Placeholder | Resolution Source | Default |
| --- | --- | --- |
| `{FEATURES_DIR}` | project-config.paths.features | `src/features` |
| `{DOCS_DIR}` | project-config.paths.docs_features | `docs/features` |
| `{COMPONENT_EXT}` | project-config.conventions.component_extension | `.tsx` |
| `{FEATURE_LAYERS}` | project-config.conventions.feature_structure | `["types","api","hooks","components"]` |

**Resolution**: `Read project-config.json → Resolve placeholders → Use resolved values`
**Fallback**: If project-config.json does not exist, use Default column

**FORBIDDEN**: Never use literal `src/features/` or `src/shared/` in generated code, commands, or file paths.

### Phase 0: Context Validation (CONTEXT.json Verification)

> **Mandatory Prerequisite**: CONTEXT.json generated by feature-architect must exist.

1. **Verify CONTEXT.json Existence**:

   ```
   Check if docs/features/<feature-id>/CONTEXT.json exists
   ├── Exists → Proceed to Phase 1
   └── Missing → Error: "CONTEXT.json does not exist. Run feature-architect first."
   ```

2. **Load and Validate CONTEXT.json**:

   ```
   Verify mandatory fields in CONTEXT.json:
   ├── feature_id
   ├── title
   ├── why
   └── quick_resume.current_state == "SpecDrafting"
   ```

3. **Extract Feature Information**:
   - Read why, user_story, requirements, assumptions from CONTEXT.json
   - If additional inputs are provided, merge with CONTEXT information

4. **Validate and Extract BRIEF.md**:

   ```
   Check BRIEF.md at artifacts.brief path in CONTEXT.json
   ├── Exists → Extract the following information from BRIEF:
   |   ├── Section 0: Raw request (reference for intent when designing FRs)
   |   ├── Section 2: User Stories → Basis for mapping to FRs
   |   ├── Section 4: BDD AC → Reference for FR AC
   |   ├── Section 5: In/Out Scope → SPEC §1.4 Goals/Non-Goals
   |   └── Section 6: Constraints → Reflected in SPEC §0
   └── Missing → Warning: "BRIEF.md does not exist. Intent traceability is limited."
                 (Non-fatal warning — continue with SPEC generation)
   ```

5. **Output Validation Results**:

   ```markdown
   CONTEXT.json validation complete

   **Feature ID**: 001-user-dashboard
   **Feature Name**: User Dashboard

   **Elements extracted from CONTEXT**:

   - Why: Improve work efficiency by 30%
   - User Story: As a user, I want to manage my dashboard
   - Requirements: Add/remove/favorite widgets

   → Commencing context discovery for SPEC generation.
   ```

### Phase 1: Context Discovery

1. **Reference CONTEXT.json** (Read-Only):
   - Read `docs/features/<feature-id>/CONTEXT.json` (validated in Phase 0)
   - Inspect related code/spec paths in references section
   - **Do not create CONTEXT.json in this step** (responsibility of feature-architect)

2. **Gather Required Files**:

   | Category | File | Required | Extracted Information |
   | --- | --- | :---: | --- |
   | **Type Definitions** | `{FEATURES_DIR}/<feature>/types/*.ts` | Required | TypeScript interfaces, Zod schemas |
   | **API Route** | API routes in `{SOURCE_ROOT}` (per framework conventions) | Conditional* | Response schema, error codes |
   | **Existing SPECs** | `docs/features/*/SPEC-*.md` | Optional | Reference patterns |
   | **Existing Code** | `{FEATURES_DIR}/<feature>/components/`, `{FEATURES_DIR}/<feature>/hooks/`, `{FEATURES_DIR}/<feature>/api/` | Optional | Existing patterns |
   | **Design Assets** | `docs/features/<feature-id>/design/` | Optional | Color tokens, layout references |
   | **UI Flow SSOT** | `docs/ui-flow/ui-flow.json` | Required | Existing panels/states/SSE/phase definitions |

   > Conditional* = Required if the feature uses API Routes

3. **CONTEXT.json references Section** (Related Code Information):
   ```json
   {
     "references": {
       "related_specs": ["SPEC-003-notification-settings.md"],
       "related_code": {
         "components": ["{FEATURES_DIR}/dashboard/components/*.tsx"],
         "hooks": ["{FEATURES_DIR}/dashboard/hooks/*.ts"],
         "api": ["{FEATURES_DIR}/dashboard/api/*.ts"]
       },
       "api_routes": ["{SOURCE_ROOT}/api/dashboard/ (framework-specific path)"]
     }
   }
   ```

### Phase 2: Interactive Clarification

> **Principle**: Compress questions to at most 7 items for user clarification

#### Q&A → BRIEF.md Logging Protocol

> Record each Question-Answer pair from Phase 2 in Section 8 (Clarification Log) of BRIEF.md.

**Logging Procedure**:

1. Pose question to user and receive answer
2. Add row to Section 8 table in BRIEF.md:
   ```markdown
   | {Number} | {Question Content} | {Answer Content} | {Impacted Section} | {Date} |
   ```
3. Update corresponding sections of BRIEF.md based on answer (e.g., update Section 5 if Scope changes)

**Example**:

```markdown
| 1 | How should offline data addition be handled? | Save locally and sync later | §5 Scope, §6 Constraints | 2026-02-11 |
| 2 | Error presentation style? | Toast | §4 AC-03 | 2026-02-11 |
```

#### 7-Question Upper Limit Rule (Autonomy Control)

| Question Count | State | Behavior |
| :---: | --- | --- |
| 1-6 | Normal | Wait after asking question |
| 7 | Limit Reached | **Autonomously halt** after 7th question |
| > 7 | AwaitingUser | No further questions allowed; select defaults |

**Handling upon reaching 7-question limit**:

1. Set `quick_resume.question_count` to 7 in CONTEXT.json
2. Transition `quick_resume.current_state` to `AwaitingUser`
3. For unanswered items, **auto-select defaults (recommended options)** or **record as Assumptions**
4. Notify user of reaching the limit:

   ```markdown
   7-Question Upper Limit Reached

   Unanswered items have been automatically selected with recommended options:

   - Q4: Offline behavior → "Save locally and sync later" (Recommended)
   - Q5: Error presentation → "Toast" (Recommended)

   Please reply if you wish to change these assumptions.
   Otherwise, SPEC generation will proceed.
   ```

**CONTEXT.json question_count Update**:

```json
{
  "quick_resume": {
    "question_count": 3,
    "current_state": "SpecDrafting"
  },
  "autonomy_control": {
    "max_questions_per_session": 7,
    "current_autonomy_level": "supervised"
  }
}
```

**Question Categories** (select only what is necessary from each category):

| Category | Example Questions |
| --- | --- |
| **Screen / UX** | New screen vs. extending existing screen? Error presentation (toast/dialog)? |
| **State Management** | State scope (per-screen/global)? Failure states included? |
| **Data** | New data structures needed? API integration approach? |
| **Testing** | Integration test scope? Mocking policy? |
| **Product / Engagement** | Engagement core loop? Aha Moment? Free vs. Paid boundary? |

**Question Format**:

```markdown
## Clarification Questions for SPEC Generation

Based on analyzing the input, the following items require confirmation:

### Q1. Screen Composition [UX]

Would you like to add this feature as a **new panel** or **integrate into an existing panel**?

- [ ] A: New panel (add to layout)
- [ ] B: Integrate as a section within existing panel (Recommended)

### Q2. Data Integration [DATA]

How should data integration with the API be handled?

- [ ] A: Real-time streaming (Recommended)
- [ ] B: Polling
- [ ] C: Exclude from MVP

(Maximum 7 questions)
```

### Phase 3: SPEC Generation

1. **Present 2 Options** (Conservative vs. Expansive):

   ```markdown
   ## SPEC Draft Proposal

   ### Option A: Conservative Approach

   - Reuse existing systems
   - 1 new data structure
   - Implementation complexity: Low

   ### Option B: Expansive Approach

   - Introduce custom algorithms
   - 3 new data structures
   - Implementation complexity: High

   Which direction would you prefer to proceed with?
   ```

2. **Generate SPEC Following User Selection**:
   - Generate `SPEC-<NNN>-<feature-name>.md`
   - Generate `screens/<screen-name>.md` (**Mandatory / Optional check per feature_type** — see below)

   **Screen Document Generation Rules** (Based on feature_type):

   | feature_type | screens/ Generation | Condition |
   | :---: | :---: | --- |
   | **ui_feature** | **Mandatory** | At least 1 Screen document required. Missing screen triggers Readiness Gate No-Go |
   | backend_feature | Not Required | Server logic only — Screens not applicable |
   | system_feature | Optional | Generate if user-facing UI (e.g. settings UI) exists |

   > **Always inspect the `feature_type` field in CONTEXT.json** to determine this.
   > If `feature_type` is null or unset, infer the presence of UI screens from BRIEF/SPEC contents.

   **Generate §6.5 Product Requirements** (User-facing features only):
   - BRIEF §5.5 → SPEC §6.5.1 Engagement Loop (Hook Model 4 phases → implementable trigger/reward mechanisms)
   - BRIEF §5.6 → SPEC §6.5.2 Competitive Context (Differentiation points → reflected in implementation priorities)
   - BRIEF §5.7 → SPEC §6.5.3 Conversion Design (Soft Paywall trigger conditions → decompose into FRs)
   - Backend-only features: Mark §6.5 as "N/A - Backend-only"

3. **Auto-generate Screen Document §13 Design Reference**:

   ```
   Check if docs/features/<feature-id>/design/ directory exists
   ├── Exists → Add §13 Design Reference to Screen document:
   |   ├── File list in design/ → Generate file table
   |   ├── If code.html exists → Extract color tokens (include warnings regarding hex → Theme mapping)
   |   ├── Discrepancies between Screen Doc and design → Generate delta table
   |   └── Update artifacts.design_assets in CONTEXT.json
   └── Missing → Omit §13 (do not create directory)
   ```

   > **SSOT Principle**: §13 is for visual reference only; Screen Doc §3–§8 serves as the authoritative implementation contract.

4. **Generate §1.5 UI Flow Contract** (Mandatory for ui_feature):

   > Reference `docs/ui-flow/ui-flow.json` collected in Phase 1 to generate §1.5

   ```
   feature_type Evaluation:
   ├── ui_feature → §1.5 UI Flow Contract is mandatory
   ├── backend_feature → "N/A - UI Flow Contract omitted for backend-only feature"
   └── system_feature → Generate only if UI screens exist
   ```

   **Generation Process**:

   ```
   1. Read existing panels/sse_mapping/phases from ui-flow.json
   2. Identify panels added/modified by this feature:
      ├── New panel → operation: "new", define visibility conditions
      ├── Modify existing → operation: "modify", describe modifications
      └── Reference only → operation: "reference"
   3. Generate §1.5.1 Panel Declarations Table
   4. Generate §1.5.2 SSE Event Mapping Table
   5. Generate §1.5.3 Phase Integration Table
   6. Generate §1.5.4 State Transition Diagram
   7. Generate json:schema/ui_flow_contract block (machine-readable)
   ```

   **Validation**: Verify that `panels[].name` follows naming conventions in existing ui-flow.json.

### Phase 3.5: API Contract & NFR Generation (Mandatory)

> "Always Required" - Ensures AI clearly understands API contracts and quality criteria

#### API Contract (Mandatory)

**Decision Criteria**:

```
API Route Usage:
├── Not used → State "N/A - Client-side only" (empty sections prohibited)
├── Used (1-2 endpoints)
|   └── Document directly in SPEC API Contract section
└── Used (3+ endpoints)
    └── Create separate API-{NNN}-{name}.md + Link from SPEC
```

**Mandatory API Contract Elements**:

| Element | Required | Description |
| --- | :---: | --- |
| Endpoint List | Required | Method, Path, Auth requirements |
| Request Schema | Required | Zod Schema (required, properties) |
| Response Schema | Required | Zod Schema (status, data, error) |
| Error Codes | Required | HTTP status code, App error code, client handling |

**Schema Extraction Process**:

```
1. Read route.ts of API Route
2. Search for Zod schemas or response type definitions
3. Extract error codes from error handling logic
4. Document in schema format within API Contract section
```

**SSOT Principle Notice**:

```markdown
> **SSOT Principle**
>
> Zod schemas / type definitions in code serve as the single source of truth.
> This document reflects the code; in the event of any conflict, the code takes precedence.
>
> API Route code location: API routes directory in `{SOURCE_ROOT}` (framework-specific)
```

#### Verified Dependencies (Mandatory)

> Record compatibility verification status for external APIs / services / libraries.

| External System | Purpose | API / SDK | verified | verification_source | verified_at |
| --- | --- | --- | :---: | --- | --- |
| Supabase Auth | Auth | supabase-js v2 | true | context7: supabase/auth | 2026-03-26 |
| Google Maps | Maps | @googlemaps/api | false | - | - |

**Verification Criteria**:
- `true`: API compatibility/version verified via context7 MCP or WebSearch
- `false`: Estimated from AI knowledge only. Requires confirmation during implementation. Automatically reflected in risk section.

**Machine-Readable Block** (Included in SPEC):
```json:schema/verified_dependencies
{
  "dependencies": [
    {
      "name": "Service Name",
      "purpose": "Purpose",
      "api_version": "SDK/API Version",
      "verified": true,
      "verification_source": "context7 or WebSearch source",
      "verified_at": "ISO 8601"
    }
  ],
  "unverified_count": 0,
  "risk_level": "low|medium|high"
}
```

> **Gate**: If `unverified_count > 0`, automatically add "Unverified External Dependencies" risk to the risk section.

#### NFR (Mandatory)

> Specify performance, concurrency, cost, and observability requirements

**Mandatory Items**:

| Item | Required | When Not Applicable |
| --- | :---: | --- |
| Performance (Response Time) | Required | "Standard CRUD - Default policy applies" |
| Reliability (Retries) | Required | Explicit retry policy required |
| Cost (When using AI) | Conditional* | N/A (AI not used) |
| Observability | Optional | "Standard logging applies" |

> Conditional* = Mandatory only for features utilizing AI/LLMs

**Question when deciding separation (within 7-question limit)**:

When API complexity is uncertain, confirm with user:

```markdown
### Q. API Document Separation [API]

There are 3 or more API Routes or the API contract is complex. How would you like to handle this?

- [ ] A: Integrate within SPEC (Recommended for simplification)
- [ ] B: Separate into standalone API-{NNN}.md (When detailed management is required)
```

### Phase 3.7: Parallel Implementation Guide Generation

> **Applicability**: Generate only when feature has 3 or more FRs. For 2 or fewer FRs, mark as `N/A - Sequential implementation`.

#### Generation Process

1. **FR Dependency Analysis** (layer-based automatic inference):

   ```
   Type/Schema FR  → No depends_on
   Hook FR         → Depends on Type/Schema
   Component FR    → Depends on Hook
   API Route FR    → Independent (Server-side)
   ```

2. **Topological Sort** → Automatically compute parallel batches

3. **Classify FR files into Foundation / Backend / Frontend / Test**

4. **Generate §0.10 and §0.11 Sections**

#### §0.10 FR Dependency Graph Template

```markdown
### 0.10 FR Dependency Graph

#### 0.10.1 Dependency Table

| FR-ID | Description | depends_on | Layer | Complexity |
| :---: | --- | :---: | --- | :---: |
| FR-{NNN}01 | {Description} | - | Type/Schema | S |
| FR-{NNN}02 | {Description} | FR-{NNN}01 | Hook | M |
| FR-{NNN}03 | {Description} | FR-{NNN}01 | Hook | M |
| FR-{NNN}04 | {Description} | 02, 03 | Component | L |
| FR-{NNN}05 | {Description} | - | API Route | M |

Layer: Type/Schema | Hook | Component | API Route | Page
Complexity: S (<50 LOC) | M (50-150) | L (150-300) | XL (300+)

#### 0.10.2 Parallel Batches (Topological Sort)

| Batch | FR List | Parallelizable | Estimated Time |
| :---: | --- | :---: | :---: |
| B1 | FR-01, FR-05 | Yes | N mins |
| B2 | FR-02, FR-03 | Yes | N mins |
| B3 | FR-04 | No | N mins |
```

#### §0.11 Parallel Work Units Template

```markdown
### 0.11 Parallel Work Units

#### 0.11.1 Foundation (Lead Agent)

| Item | File | Related FR |
| --- | --- | :---: |
| Zod Schema | `types/*.ts` | ALL |
| Hook Interface | `hooks/*.ts` | ALL |
| Barrel File | `index.ts` | ALL |

#### 0.11.2 Backend Work Units

| PWU-ID | FR-ID | Task | File |
| :---: | :---: | --- | --- |
| BE-01 | FR-XX | {Description} | `api/*.ts` |
| BE-02 | FR-XX | {Description} | `{SOURCE_ROOT}/api/*/route.{ext}` (per framework) |

#### 0.11.3 Frontend Work Units

| PWU-ID | FR-ID | Task | File |
| :---: | :---: | --- | --- |
| FE-01 | FR-XX | {Description} | `hooks/*.ts` |
| FE-02 | FR-XX | {Description} | `components/*.tsx` |

#### 0.11.4 Test Work Units

| PWU-ID | FR-ID | Target | File |
| :---: | :---: | --- | --- |
| TEST-01 | FR-XX | Hook | `tests/unit/features/.../hooks/*.test.ts` |
| TEST-02 | FR-XX | Component | `tests/unit/features/.../components/*.test.tsx` |

#### 0.11.5 Integration Checklist

- [ ] Hook → Connect to real API
- [ ] Component → Bind to real Hook
- [ ] make q.lint: 0 errors
- [ ] make q.test: all pass
```

### Phase 4: Validation & Handover

0. **BRIEF <-> SPEC Traceability Mapping** (When BRIEF exists):

   > When BRIEF.md exists, populate the traceability section of CONTEXT.json.

   **Mapping Process**:

   ```
   1. Extract User Story IDs from BRIEF Section 2 (US-01, US-02, ...)
   2. Extract BDD AC names from BRIEF Section 4 (AC-01, AC-02, ...)
   3. Extract FR IDs from generated SPEC (FR-XXXNN)
   4. Create mappings:
      - user_story_to_fr: Map each US → Related FRs
      - bdd_to_fr: Map each AC → Related FRs
   5. Record unmapped items in unmapped_* arrays
   6. Save to traceability section in CONTEXT.json
   ```

   **CONTEXT.json Update Example**:

   ```json
   {
     "traceability": {
       "user_story_to_fr": [
         { "user_story_id": "US-01", "fr_ids": ["FR-00101", "FR-00102"] },
         { "user_story_id": "US-02", "fr_ids": ["FR-00103"] }
       ],
       "bdd_to_fr": [
         { "scenario_name": "AC-01", "fr_ids": ["FR-00101"] },
         { "scenario_name": "AC-02", "fr_ids": ["FR-00102", "FR-00103"] }
       ],
       "unmapped_user_stories": [],
       "unmapped_bdd_scenarios": [],
       "validated_at": null
     }
   }
   ```

   **Handling Unmapped Items**: Output a warning if entries exist in unmapped arrays:

   ```markdown
   Traceability Warning:

   - US-03: No FR mapping found (Confirm if Out of Scope)
   - AC-04: No FR mapping found
   ```

1. **Cross-Reference Validation** (Mandatory):

   > **Purpose**: Verify that items defined in Target Files are properly reflected in Data Schema.

   | Defined Item | Mandatory Target Files Item | Validation |
   | --- | --- | :---: |
   | New Zod Schema | `Type/Schema` layer + file path | OK |
   | New API Route | `API Route` layer + directory | OK |

   **Validation Process**:

   ```
   1. Check if new Zod schema is defined
      ├── Defined → Verify Type/Schema layer exists in Target Files
      |   ├── Exists → Pass
      |   └── Missing → Addition required: `{FEATURES_DIR}/{feature}/types/{schema}.ts`
      └── Reusing existing only → N/A (Type/Schema layer may be omitted)

   2. Check if new API Route is defined
      ├── Defined → Verify API Route layer exists in Target Files
      └── Reusing existing/N/A → API Route layer may be omitted
   ```

   **Auto-remediation**: Automatically add missing layers to §0.1 Target Files if validation fails.

1-B. **§0.10/§0.11 Cross-Validation** (When FR count is 3+):

| Validation Item | Condition | Result |
| --- | --- | :---: |
| All FRs registered in §0.10 | FR list in §2 ↔ §0.10 Dependency Table | OK |
| No circular dependencies | No cycles in depends_on graph | OK |
| §0.1 Files ↔ §0.11 PWU Mapping | All files in Target Files assigned to PWUs | OK |
| Foundation Completeness | All Zod schemas + Hook Interfaces registered in §0.11.1 | OK |

**Validation Process**:

```
1. Extract FR list in §2 → Cross-check against §0.10 Dependency Table
   ├── All registered → Pass
   └── Missing FR found → Add to §0.10
2. Detect cycles in depends_on graph (DFS-based)
   ├── No cycles → Pass
   └── Cycle detected → Redesign dependencies
3. Validate mapping from §0.1 Target Files → §0.11 PWUs
   ├── All mapped → Pass
   └── Unmapped file found → Assign to appropriate PWU
```

## Failure Mode Handling

| Case | Handling |
| --- | --- |
| **Insufficient Input** | Supplement via core questions in Phase 2, collect minimum requirements |
| **Unimplementable due to technical constraints** | Provide alternative (Plan B) alongside in SPEC |
| **Ambiguous User Answer** | Proceed with default (recommended option), explicitly state "Assumption" in SPEC |
| **7-Question Limit Reached** | Auto-select recommended option for unanswered items, state assumption in SPEC |
| **Tier 1 Security Task Detected** | Autonomously halt, require user confirmation (Auth/Payment/PII related) |

## AI Behavioral Guidelines

### DO

- Reflect input requirements across all FRs in SPEC
- Reference existing patterns (read similar SPEC files)
- Compress questions to at most 7 items
- Explicitly record assumptions (Assumption)
- Specify test paths concretely

### DON'T

- Write SPEC ignoring input requirements
- Decide to add new data structures without user confirmation
- Generate SPEC with empty sections (explicitly state "N/A - Not Applicable" if no content)
- Generate voluminous documents at PRD level (SPEC focuses on a single feature)
