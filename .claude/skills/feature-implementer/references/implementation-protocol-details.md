# Feature Implementer

> **Core Concept**: The Executor from design to code ("The Executor")

This skill takes SPEC.md and Screen documents generated by `feature-spec-generator` as input and implements tests and code strictly following TDD principles.

## Target Tech Stack Assumptions (MUST)

> **Important**: This skill is tailored to the target project's tech stack.

| Item | Stack | Details |
| --- | --- | --- |
| **Architecture** | Feature-First + Simplified Clean Architecture | Based on `project-config.paths.features` (Default: `src/features/`) |
| **State Management** | Per framework in `project-config.json` | Standard framework state management patterns |
| **Data Model** | Zod schema | Type definitions with runtime validation |
| **Error Handling** | try-catch + logger | Fail-Fast principle |
| **Testing** | `project-config.quality.test_framework` | Standard framework test patterns |

## Protocol

### PATH CONTRACT (MANDATORY)

> **BINDING**: This skill uses dynamic path placeholders.
> The AI must resolve paths from `project-config.json` before performing file operations.
> Using literal paths is a **protocol violation**.

| Placeholder | Resolution Source | Default |
| --- | --- | --- |
| `{FEATURES_DIR}` | `project-config.paths.features` | `src/features` |
| `{TESTS_DIR}` | `project-config.paths.tests_unit` | `tests/unit` |
| `{COMPONENT_EXT}` | `project-config.conventions.component_extension` | `.tsx` |
| `{FEATURE_LAYERS}` | `project-config.conventions.feature_structure` | `["types","api","hooks","components"]` |

**Resolution**: `Read project-config.json → Resolve placeholders → Use resolved values`
**Fallback**: If project-config.json does not exist, use Default column

**FORBIDDEN**: Never use literal `src/features/` or `tests/unit/` in generated code, commands, or file paths.

### Phase 0: Pre-Validation

1. **Mandatory Review of CLAUDE.md Architecture Rules** (MUST):
   - Review the "Architecture Overview" and "Feature-First Dependency Rules" sections in `CLAUDE.md`.
   - Verify Feature-First dependency boundaries.
   - Confirm standard project directory structure.

   > **Never begin implementation without completing this check.**

2. **Load SPEC**: Read `docs/features/<feature-id>/SPEC-<NNN>-*.md`.
3. **Completeness Check**: Confirm presence of mandatory sections:
   - `## 0. AI Implementation Contract` - Target Files, State/Hook, Error Handling, Data Model
   - `## 2. Functional Requirements` - Per-FR specifications
   - `## 3. Dependencies & Risks` - API contracts
4. **Reject on Incompleteness**: If SPEC is incomplete, reject back to `feature-spec-generator`:

   ```
   SPEC Incomplete - Rejecting to Generator

   Missing items:
   - [ ] §0.2 State/Hook structure not defined
   - [ ] §0.4 Data Model not defined

   → Run /feature-spec-generator to supplement the SPEC.
   ```

5. **Reference CONTEXT.json**: Review Hard Constraints (identify non-negotiable boundaries).

6. **Reference UI Flow SSOT** (MUST for ui_feature):
   - Read `docs/ui-flow/ui-flow.json` to identify:
     - Existing panel list and visibility conditions
     - SSE events → state transition mappings
     - Phase layout composition
   - Cross-check against the `json:schema/ui_flow_contract` block in SPEC §1.5 UI Flow Contract.
   - Panels marked `operation: "new"` must be added to `ui-flow.json` upon implementation completion (verified in feature-wiring).

### Phase 1: Implementation Planning

1. **Analyze Target Files**:
   - Extract implementation target file list from SPEC §0.1.
   - Classify by status: Completed / In Progress / Pending.

2. **Construct Dependency Graph** (Feature-First Baseline):

   ```
   [Type + Zod Schema] → [API Layer] → [Custom Hook] → [UI Component]
         ↓                    ↓              ↓               ↓
   {FEATURES_DIR}/<feature>/{layer1}/  →  {layer2}/  →  {layer3}/  →  {layer4}/
   # FEATURES_DIR = project-config.paths.features (Default: src/features)
   # Layer sequence = project-config.conventions.feature_structure (Default: types → api → hooks → components)
   ```

3. **Determine Implementation Sequence** (Bottom-Up):
   ```
   1. Type + Zod Schema (Type definitions + validation) ─┐
   2. API Layer (fetch / API Route)                     ─┘ Can be parallelized
   3. Custom Hook (useXxx)
   4. Component / Page (UI)
   5. Test (Each layer)
   ```

### Phase 2: TDD Cycle (Red-Green-Refactor)

> **Principle**: Write tests before implementing code for each file.
> **REQUIRED RULE**: `R-CM-011` (testing-anti-patterns) — Never test mock mechanics, no test-only methods, no ungrounded mocking.
> **REQUIRED RULE**: `R-CM-010` (verification-before-completion) — Fresh verification evidence mandatory before claiming completion.

**Single File Implementation Cycle**:

```
+-------------------------------------------------------------+
| 1. RED: Write failing tests                                 |
|    - Convert SPEC AC (Acceptance Criteria) to test cases    |
|    - Convert SPEC EC (Edge Cases) to additional tests       |
|    - Run `make q.test` or project-config test command → Verify failure |
+-------------------------------------------------------------+
| 2. GREEN: Implement minimal code to pass tests              |
|    - Reference SPEC "AI Implementation Hints"               |
|    - Follow existing patterns (project conventions)         |
|    - Run `make q.test` or project-config test command → Verify pass |
+-------------------------------------------------------------+
| 3. REFACTOR: Improve code quality                           |
|    - Remove duplication, refine naming                      |
|    - Run `make q.check` or project-config lint command → Verify zero warnings |
|    - Verify tests continue to pass                          |
+-------------------------------------------------------------+
```

### Phase 3: FR Implementation

Implement each FR (Functional Requirement) from the SPEC sequentially.

**FR Implementation Checklist**:

> **CHECKLIST UPDATE RULE (MANDATORY)**:
> During implementation of each FR, re-output the checklist and update `[ ]` to `[x]` as test writing, implementation, and quality validation items complete.
> Confirm all items are marked `[x]` before moving to the next FR.
> **Proceeding to the next step without updating = Violation Protocol infraction (severity: HIGH).**

```markdown
## Implement FR-NNNNN

### Test Authoring (Red)

- [ ] Unit Test: Author `{TESTS_DIR}/features/<feature>/<name>.test.ts(x)`
- [ ] Author test cases per AC
- [ ] Author edge case tests per EC
- [ ] Run `make q.test` or project-config test command → Verify failure

### Code Implementation (Green)

- [ ] Implement Type + Zod Schema (if required)
- [ ] Implement API Layer (if required)
- [ ] Implement Custom Hook (if required)
- [ ] Implement Component/Page (if required)
- [ ] Run `make q.test` or project-config test command → Verify pass

### Quality Validation (Refactor)

- [ ] Pass `make q.check` or project-config lint command
- [ ] Remove code duplication
- [ ] Verify compliance with SPEC Error Handling Policy
```

### Phase 4: Integration & Handover

1. **Run Full Test Suite**:

   ```bash
   make q.test
   # Or test command per project-config.quality.test_framework
   ```

2. **Lint Verification**:

   ```bash
   make q.check
   # Or lint command per project-config.quality.linter
   ```

3. **Update SPEC Status**:
   - Update Target Files status in SPEC §0.1 to completed.
   - Record implementation completion in Revision History (§5).

4. **Handover Message**:

   ```markdown
   Implementation complete

   Created/modified files:

   - {FEATURES_DIR}/<feature>/types/index.ts (New)
   - {FEATURES_DIR}/<feature>/api/<feature>-api.ts (New)
   - {FEATURES_DIR}/<feature>/hooks/use-<feature>.ts (New)
   - {FEATURES_DIR}/<feature>/components/<Feature>Panel.tsx (New)
   - {FEATURES_DIR}/<feature>/index.ts (Barrel file updated)
   - {TESTS_DIR}/features/<feature>/use-<feature>.test.ts (New)

   - Total tests: N passed
   - New tests: M added

   Next steps:
   → Run /feature-wiring <feature-id> to perform integration verification.
   ```

## Implementation Principles

### 1. SPEC is the Single Source of Truth

| Item | Reference Location |
| --- | --- |
| Data Model | SPEC §0.4 Data Model |
| State Structure | SPEC §0.2 State/Hook |
| Error Handling | SPEC §0.3 Error Handling Policy |
| Acceptance Criteria | SPEC §2 AC for each FR |
| Edge Cases | SPEC §2 EC for each FR |
| Implementation Hints | SPEC §2 "AI Implementation Hints" for each FR |

### 2. Strict Compliance with Hard Constraints

Hard Constraints in `CONTEXT.json` **must never be violated under any circumstance**.

```markdown
## Immediately stop and report to user upon violation

Examples:

- "No DB Schema Changes" → New table required → Stop & Report
- "No External Package Additions" → New package required → Stop & Report
```

### 3. Follow Existing Patterns (Project Standards)

| Pattern | Project Convention |
| --- | --- |
| **Folder Structure** | `{FEATURES_DIR}/{name}/types/`, etc. |
| **Import Rules** | Barrel file (`index.ts`) only; direct internal imports prohibited |
| **State Management** | Standard framework patterns (see `project-config.json`) |
| **Error Handling** | `try-catch` + logger |
| **Data Model** | `interface` + `z.object()` (Zod schema) |
| **API Layer** | `async function` + `fetch` |
| **Test Mocking** | Standard framework mocking patterns (see `project-config.quality.test_framework`) |
| **Naming** | kebab-case filenames, PascalCase component names |
| **UI Text** | Sourced via `messages.ts` (hardcoding prohibited) |

### 4. Incremental Implementation

Never implement everything in a single monolithic pass.

```
BAD:  Batch-generating all files at once
GOOD: One FR → Test → Implement → Verify → Next FR
```

## Code Templates

### Type + Zod Schema

```typescript
// {FEATURES_DIR}/<feature>/types/index.ts

import { z } from 'zod';

/** [Feature Name] Data Model Schema */
export const xxxSchema = z.object({
  id: z.string(),
  name: z.string(),
  // ... fields
});

/** [Feature Name] Data Model Type */
export type XxxModel = z.infer<typeof xxxSchema>;
```

### API Layer

```typescript
// {FEATURES_DIR}/<feature>/api/<feature>-api.ts

import { xxxSchema, type XxxModel } from '../types';
import { logger } from '@/shared/lib/logger';

const TAG = 'XxxApi';

/**
 * [Feature Name] Data Fetch
 *
 * @param id - Target ID
 * @returns Data (null on failure)
 */
export async function fetchXxx(id: string): Promise<XxxModel | null> {
  try {
    const response = await fetch(`/api/xxx/${id}`);
    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }
    const data = await response.json();
    return xxxSchema.parse(data);
  } catch (error) {
    logger.error(TAG, 'Error fetching xxx', error);
    return null;
  }
}
```

### Custom Hook

```typescript
// {FEATURES_DIR}/<feature>/hooks/use-<feature>.ts

// Add framework directives if needed (e.g., 'use client' for Next.js App Router)

// Standard framework state management imports (e.g., React useState/useEffect/useCallback)
import { fetchXxx } from '../api/<feature>-api';
import { type XxxModel } from '../types';
import { MESSAGES } from '@/shared/constants/messages';
import { logger } from '@/shared/lib/logger';

const TAG = 'useXxx';

/** [Feature Name] Hook State */
interface XxxState {
  data: XxxModel | null;
  isLoading: boolean;
  error: string | null;
}

/**
 * [Feature Name] Custom Hook
 *
 * @param id - Target ID
 * @returns State and actions
 */
export function useXxx(id: string) {
  const [state, setState] = useState<XxxState>({
    data: null,
    isLoading: true,
    error: null,
  });

  useEffect(() => {
    let cancelled = false;

    async function load() {
      try {
        logger.debug(TAG, `Loading xxx: ${id}`);
        const data = await fetchXxx(id);

        if (cancelled) return;

        if (data === null) {
          setState({ data: null, isLoading: false, error: MESSAGES.errors.dataNotFound });
          return;
        }

        setState({ data, isLoading: false, error: null });
      } catch (error) {
        if (cancelled) return;
        logger.error(TAG, 'Error loading xxx', error);
        setState({ data: null, isLoading: false, error: MESSAGES.errors.loadFailed });
      }
    }

    load();
    return () => {
      cancelled = true;
    };
  }, [id]);

  const doSomething = useCallback(async () => {
    setState((prev) => ({ ...prev, isLoading: true }));

    try {
      // Business logic
      setState((prev) => ({ ...prev, isLoading: false }));
    } catch (error) {
      logger.error(TAG, 'Error doing something', error);
      setState((prev) => ({
        ...prev,
        isLoading: false,
        error: MESSAGES.errors.operationFailed,
      }));
    }
  }, []);

  return { ...state, doSomething };
}
```

## Test Authoring Guide

### Test File Structure

```typescript
// {TESTS_DIR}/features/<feature>/hooks/use-<feature>.test.ts

// Imports per project-config.quality.test_framework
// Example (Vitest + React Testing Library):
//   import { renderHook, waitFor } from '@testing-library/react';
//   import { vi, describe, it, expect, beforeEach } from 'vitest';
// Example (Flutter):
//   import 'package:flutter_test/flutter_test.dart';
// Example (Jest):
//   import { renderHook, waitFor } from '@testing-library/react';
import { useXxx } from '@/features/<feature>/hooks/use-<feature>';
import * as xxxApi from '@/features/<feature>/api/<feature>-api';
import type { XxxModel } from '@/features/<feature>/types';

// Standard mocking pattern (e.g., vi.mock in Vitest, jest.mock in Jest)
// vi.mock('@/features/<feature>/api/<feature>-api');

describe('useXxx', () => {
  const mockData: XxxModel = { id: 'test-id', name: 'Test' };

  beforeEach(() => {
    vi.resetAllMocks();
  });

  // AC-based Test
  describe('AC1: Successful Data Load', () => {
    it('should load data successfully when service returns data', async () => {
      // Arrange
      vi.mocked(xxxApi.fetchXxx).mockResolvedValue(mockData);

      // Act
      const { result } = renderHook(() => useXxx('test-id'));

      // Assert
      await waitFor(() => {
        expect(result.current.isLoading).toBe(false);
      });
      expect(result.current.data).toEqual(mockData);
      expect(result.current.error).toBeNull();
    });
  });

  // EC-based Test
  describe('EC1: No Data', () => {
    it('should set error state when service returns null', async () => {
      // Arrange
      vi.mocked(xxxApi.fetchXxx).mockResolvedValue(null);

      // Act
      const { result } = renderHook(() => useXxx('test-id'));

      // Assert
      await waitFor(() => {
        expect(result.current.isLoading).toBe(false);
      });
      expect(result.current.data).toBeNull();
      expect(result.current.error).toBeTruthy();
    });
  });

  describe('EC2: Network Error', () => {
    it('should set error state when service throws exception', async () => {
      // Arrange
      vi.mocked(xxxApi.fetchXxx).mockRejectedValue(new Error('Network error'));

      // Act
      const { result } = renderHook(() => useXxx('test-id'));

      // Assert
      await waitFor(() => {
        expect(result.current.isLoading).toBe(false);
      });
      expect(result.current.data).toBeNull();
      expect(result.current.error).toBeTruthy();
    });
  });
});
```

### AC/EC → Test Conversion Rules

> **BDD 5-column Table Mapping**: Directly translate SPEC AC tables into test code

| BDD Column | Test Mapping | Role in Code |
| --- | --- | --- |
| **Given (Precondition)** | Arrange (`beforeEach`, Mock setup) | `vi.mocked(api.method).mockResolvedValue(...)` |
| **When (Action)** | Act (Execution) | `renderHook(() => useXxx(...))` |
| **Then (Expected Result)** | Assert (Verification) | `expect(result.current.xxx).toBe(...)` |
| **Observation Point** | Target for `expect()` matcher | Specific variable names, state values |

## AI Behavioral Guidelines

### DO

- Confirm architecture rules in `CLAUDE.md` before starting implementation
- Convert all ACs from the SPEC into test cases
- Author tests before implementing code (Red-Green-Refactor)
- Reference existing patterns (inspect similar files in `{FEATURES_DIR}/`)
- Import exclusively via barrel files (`index.ts`)
- Use `try-catch` + `logger` for error handling
- Run tests after completing each FR
- Reference UI text via `messages.ts`

### DON'T

- Start implementation without reviewing `CLAUDE.md` rules
- Violate Hard Constraints in `CONTEXT.json`
- Implement code without tests
- Add un-specced features (Overengineering)
- Alter existing interface signatures (unless permitted by Soft Constraints)
- Overuse `any` type (use explicit types or `unknown` + type guards)
- Batch-create all files at once (implement incrementally)
- Author code outside the Feature directory (no legacy paths)
- Bypass barrel files with direct internal imports
- Use `console.log` (use logger)

## SDD Mode (Subagent-Driven Development)

> Aligned with: Superpowers v6.1.1, 2026-07-17 (Source: `skills/subagent-driven-development/SKILL.md` + `task-reviewer-prompt.md`)

> **Automatically activate SDD mode when `PLAN.md` exists and 3 or more independent tasks are identified.**
> If `PLAN.md` is absent, execute in standard inline TDD mode.

### What is SDD Mode?

An execution pattern where dedicated task-level subagents are dispatched to implement code, followed by a **Task Reviewer** (a single reviewer reading the diff once and returning 2 independent verdicts: spec compliance + code quality) for each task. Broad review spanning the entire branch is executed exactly once after all tasks complete (`final-review`).

**Core Principle**: Fresh subagent per task + Task Reviewer (Unified spec + quality) + single branch-wide final review = High-quality, fast iteration.

**Evolution History (v6.1.1 Re-alignment)**: Previous versions sequentially dispatched 2 separate subagents for Spec Compliance Review and Code Quality Review (2-Stage Review). Empirical measurement upstream showed excessive latency and context re-acquisition overhead, leading to unification into a single Task Reviewer returning 2 verdicts from a single diff read. Pre-Flight Plan Review, File Handoffs, Durable Progress Ledger, Model Selection, and Reviewer Prompt construction disciplines below are newly incorporated with this alignment.

### Pre-Flight Plan Review (Once prior to Task 1)

**Before** dispatching Task 1, scan `PLAN.md` once in full to identify:

- Contradictions between tasks or against Global Constraints in `PLAN.md`
- Items explicitly mandated by `PLAN.md` that the review rubric considers defects (e.g., tests asserting nothing, verbatim duplication of logic blocks)

Present all discovered items to the user in a **single batched question** — place each finding alongside the verbatim `PLAN.md` excerpt directing it to confirm which takes precedence. Do not pause iteratively across tasks. If the scan is clean, proceed without comment. Conflicts emerging only during implementation continue to be caught by the standard task review loop.

### SDD Process

```
Read PLAN.md → Pre-Flight Plan Review (Scan conflicts → Batch question) → Extract all tasks → Begin tracking via TaskCreate
  ↓
Per Task:
  1. Extract task brief: Write full task text to `.tmp/sdd/task-N-brief.md` (no inline prompt pasting — File Handoffs)
  2. Dispatch Implementer subagent (references/sdd-implementer-prompt.md) — pass brief/report file paths, specify model
  3. Handle Implementer status (DONE / DONE_WITH_CONCERNS / BLOCKED / NEEDS_CONTEXT)
  4. Create review package: Write commit list + stat + diff to `.tmp/sdd/review-<base7>..<head7>.diff`
  5. Dispatch Task Reviewer (references/sdd-task-reviewer-prompt.md) — pass 3 file paths (brief/report/diff) + Global Constraints
     → ❌ Issues → Implementer fixes → Re-review (same reviewer re-evaluates both spec + quality)
     → ✅ Passed → Task complete, append one line to `.tmp/sdd/progress.md`
  ↓
All tasks complete → Execute final-review (Single branch-wide comprehensive review)
```

### Implementer Status Handling

| Status | Action |
| --- | --- |
| **DONE** | Create review package and dispatch Task Reviewer |
| **DONE_WITH_CONCERNS** | Review concerns and proceed to Task Reviewer |
| **NEEDS_CONTEXT** | Provide missing context and re-dispatch |
| **BLOCKED** | (1) Context issue → Provide more (2) Task too large → Decompose (3) Plan error → Surface to user |

### Model Selection

**Principle**: "Turns beat token unit cost" — Cost scales with the number of turns subagents consume; cheaper models frequently consume 2-3x more turns on multi-step tasks, increasing total cost. Use mid-tier models as the baseline for reviewers and implementers working from prose descriptions. When task text contains complete code, implementation is merely transcription + testing, making lower-tier models sufficient.

| Task Complexity | Model Selection | Signals |
| --- | --- | --- |
| Mechanical (1-2 files, complete spec) | Haiku tier | Complete code included in plan |
| Integration (Multi-file, coordination needed) | Sonnet tier | Inter-file dependencies, pattern matching |
| Architecture (Design judgment, broad context) | Opus tier | Architectural decisions. **Branch final review always uses this tier** — explicitly specified, not defaulting |

**Always specify models explicitly upon dispatch.** Omitting the model causes inheritance of the session's default (typically the most expensive model), defeating the purpose of this section. Review tasks also select models according to diff size, complexity, and risk.

### File Handoffs (File-based handoffs — No raw prompt pasting)

Content pasted into dispatch prompts and subagent returns remain resident in the session context, re-read on every subsequent turn. Pass artifacts via files.

- **Task Brief**: Prior to dispatching an implementer, extract the full task text into `.tmp/sdd/task-N-brief.md` and pass only the file path in the prompt (brief2dev equivalent of upstream `scripts/task-brief` — if no dedicated script is present, the AI extracts the section directly). The dispatch prompt contains only: (1) one line on where this task sits, (2) brief path ("read first — requirements and values to use as-is"), (3) interfaces/decisions from earlier tasks unknown to the brief, (4) resolutions of ambiguities in the brief, (5) report path + report contract. Exact values (numbers, magic strings, signatures, test cases) must exist solely in the brief file.
- **Report File**: The report filename matches the brief filename (`task-N-brief.md` → `task-N-report.md`). The subagent writes the full report to the file and returns only status, commits, one-line test summary, and concerns to the controller.
- **Reviewer Inputs**: The Task Reviewer receives 3 paths (brief file, report file, review package diff file) + Global Constraints binding the task.
- Remediation dispatches append fix reports (including test outputs) to the same report file, and re-reviews read the updated file.
- Measured case: A real session dispatch reached 42k characters, 99% of which was accumulated paste of earlier task summaries. A new subagent needs only its task, touching interfaces, and Global Constraints.

**brief2dev Path Adaptation**: Upstream `.superpowers/sdd/` is translated to `.tmp/sdd/` per brief2dev conventions (`.tmp/` matches the git-ignored runtime artifact location in R-CM-034 — `PLAN.md` also resides in `.tmp/worktree-<safeBranch>/PLAN.md`). Progress ledger is `.tmp/sdd/progress.md`, task brief is `.tmp/sdd/task-N-brief.md`, and review package is `.tmp/sdd/review-<base7>..<head7>.diff`.

### Durable Progress Ledger (Compaction Survival)

Conversational context memory does not survive compaction. Controllers losing track of position and re-dispatching entire completed task sequences was observed as the costliest failure mode. Record progress in a ledger file in addition to todo items.

- Check the ledger when starting SDD mode: `cat .tmp/sdd/progress.md` (create if absent). Never re-dispatch tasks recorded as completed in the ledger — resume from the first incomplete task.
- When task review passes cleanly, append a line to the ledger in the same turn: `Task N: complete (commits <base7>..<head7>, review clean)`.
- The ledger is a recovery map — even if context forgets commit creation, commits referenced in the ledger exist in git. Post-compaction, trust the ledger and `git log` over conversational memory.

### Reviewer Prompt Construction Rules

When populating Task Reviewer dispatch prompts:

- Do not add open-ended instructions unrelated to the task (e.g., "check all call sites"). Do not ask reviewers to re-run tests the implementer already ran — the implementer's report contains test evidence.
- **Never pre-judge reviewer findings** — do not include phrases like "do not flag this" or "maximum Minor severity" in dispatch prompts. If you believe a finding is a false positive, let the reviewer raise it and evaluate within the review loop.
- Copy Global Constraints verbatim from the Global Constraints section of `PLAN.md` or the SPEC (exact values, formats, inter-component relationships). Process rules (YAGNI, test hygiene) already exist in the reviewer template.
- Hand diffs to reviewers via file. Use the BASE recorded prior to task dispatch — avoid `HEAD~1`, which truncates multi-commit tasks.
- Dispatch fix subagents for Critical/Important findings. Record Minor findings in the progress ledger, allowing the branch final review to assess whether fixes are needed before merge.
- Findings labeled "plan-mandated" represent user decisions, identical to other plan contradictions. Present the finding alongside the plan text and ask which takes precedence — do not dismiss or dispatch fixes without asking.
- When the branch final review returns findings, dispatch **one** fix subagent containing the aggregated findings list, rather than one per finding.

### Handling Reviewer ⚠️ Items

The Task Reviewer may report "⚠️ Unverifiable in Diff" items (requirements in unmodified code or spanning across tasks). These do not block the remainder of the review, but because the controller holds cross-task context, it must resolve each item before marking the task complete. If confirmed as a real gap, treat as a spec review failure — return to implementer and re-review.

### Unified Task Reviewer Rules (Replacing Legacy 2-Stage Review)

1. **Spec Compliance and Code Quality are judged together in a single diff read.** The reviewer returns both the spec compliance verdict (✅/❌/⚠️) and quality verdict (Approved/Needs fixes). Reports missing either verdict are treated as review omissions.
2. **If reviewer finds issues** → Implementer fixes → Reviewer re-reviews both spec + quality. Never skip re-review.
3. **Never dispatch implementation agents in parallel** (risk of conflicts).

> Reference: `references/gan-generator-evaluator-pattern.md` — Generator-Evaluator separation pattern. Reference when strengthening Task Reviewers.

### Test Coverage Diagram (Mandatory Prior to TDD)

**Before starting** the TDD Red-Green-Refactor cycle, read `references/test-coverage-diagram-template.md` and execute:

1. **Code Path Tracing**: Map all branch and error paths in an ASCII diagram
2. **User Flow Mapping**: Map user interaction sequences + edge cases (double click, timeout, concurrent actions)
3. **Gap Identification**: Cross-check each branch against existing tests for ★★★/★★/★ quality scoring
4. **Test Generation**: Author tests via TDD for paths marked GAP

This diagram is a design tool that determines "what tests to write" in TDD. Execute it **before writing tests**, not afterwards.
